## Scope and authority

This specification turns `docs/design/skill-window-posterior-attribution.md` sections 2–7 into an implementation contract. Accepted decisions are referenced rather than re-decided: ADR-0025 defines the bundle vocabulary for context shadowing; ADR-0026 defines the three derived stores and projection/memo boundary; ADR-0027 defines weighted multi-Skill Failure cases and dominant-only proposal gates; ADR-0028 defines the per-session emission judge. Existing meanings from ADR-0014, ADR-0015, ADR-0016, ADR-0022, and ADR-0023 remain in force.

`Experience.confidence`, `SkillDiagnosis.confidence`, and `FailureAttribution.margin` are evidence-strength values. Until a member explicitly adopts calibration output, none of them SHALL be used as a proposal gate or as an attribution weight, as required by the SKIL-133 handoff and the current `packages/skill-evolution/src/types.ts` shapes.

## Context vocabulary and windows

- **R-1** — WHEN the bundle receives `compaction/summary` or `compaction/prune`, THE SYSTEM SHALL emit a `context-shadowed` Observation whose schema-version-1 payload contains merged inclusive `shadowedSeqRanges`, `shadowedTokenCount`, and `mechanism` equal to `summary` or `prune`.
- **R-2** — WHEN the bundle receives any DSH event with `surfaceOp.op === 'replace'`, THE SYSTEM SHALL preserve the core Observation kind and add `surfaceReplace: true`; a replacement `tool/result` SHALL not be paired as an ordinary standalone tool result.
- **R-3** — WHEN the bundle emits a `skill-loaded` Observation, THE SYSTEM SHALL add optional `shadowTracked: true`; the core SHALL read these core fields and SHALL not inspect DSH-specific `payload.eventType` values.
- **R-4** — WHEN a session contains a `skill-loaded` Observation, THE SYSTEM SHALL create one `SkillWindow` beginning at that Observation and SHALL end it at the first subsequent same-session `skill-loaded`, `user-follow-up` except one with `explicit: true` and no `sessionSeq`, `task-finished`, or `context-shadowed` Observation that shadows that load.
- **R-5** — WHEN a SkillWindow ends, THE SYSTEM SHALL set `endObservationId` to the ending Observation, exclude that Observation from `stepObservationIds`, and set `endReason` to `skill-loaded`, `user-follow-up`, `task-finished`, or `context-shadowed`; WHEN no ending Observation exists THE SYSTEM SHALL set `endReason` to `open` and omit `endObservationId`.
- **R-6** — WHEN a SkillWindow is built from a `skill-loaded` Observation with `shadowTracked: true`, THE SYSTEM SHALL use `endCertainty: 'observed'`; WHEN that field is absent or the window is open THE SYSTEM SHALL use `endCertainty: 'uncertain'`.
- **R-7** — WHEN an Observation is marked `surfaceReplace: true`, THE SYSTEM SHALL exclude it from window steps and emission time steps; `skill-load-requested` and `skill-load-failed` SHALL remain ordinary window steps, and `skill-load-failed` SHALL retain composition attribution.
- **R-8** — WHEN the first Observation in a session has `sessionSeq > 0`, THE SYSTEM SHALL set `unknownPrefix: true` on the session's posterior and SHALL suppress `uncovered` classification for that session.
- **R-9** — WHEN a legacy load has no `shadowTracked` field, THE SYSTEM SHALL keep its qualification interval through session end unless an observed shadowing record ends it; a missing shadowing observation SHALL never be interpreted as proof that the Skill remained visible.

## Sequence model and emission seam

- **R-10** — WHEN posterior inference builds time steps, THE SYSTEM SHALL use SKIL-128 `ToolAttempt` pairs ordered by `sessionSeq` (or `occurredAt` when absent), exclude the `skill` tool and replacement events, and preserve the ToolAttempt fields named by ADR-0023 for emission input.
- **R-11** — WHEN posterior inference runs, THE SYSTEM SHALL process each session independently across tasks, define hidden states as `none` plus Skills that were loaded before the step and whose load remains unshadowed, and treat a Skill outside that qualification interval as structurally absent with posterior exactly zero.
- **R-12** — WHEN the sequence model transitions between steps, THE SYSTEM SHALL use stay probability `rho = 0.9`, distribute remaining mass across other eligible states, and use load-entry probability `lambda = 0.8` when a new Skill loads; the first step SHALL start at `none` with probability 1 when no load precedes it.
- **R-13** — WHEN posterior inference completes, THE SYSTEM SHALL use scaled forward-backward marginal posteriors, select each step's MAP from the marginal distribution, and compute trajectory, task, and window shares as the arithmetic mean of step posteriors, including `none`.
- **R-14** — WHEN a host supplies a `SkillEmissionJudge`, THE SYSTEM SHALL accept the ADR-0028 `DerivedJudge<EmissionInput, EmissionOutput>` shape with per-session `EmissionStep` and `EmissionSkill` inputs and a `[step][skill]` matrix of log-likelihood ratios relative to `none`.
- **R-15** — WHEN an emission judge returns a dimensionally valid matrix of finite log ratios, THE SYSTEM SHALL clamp every ratio to `[-10, 10]`; WHEN dimensions do not match, a value is non-finite, or alignment has an invalid `skillStep`, THE SYSTEM SHALL reject the result for that session and record `fallbackReason: 'invalid-output'` while using `rule-1`.
- **R-16** — WHEN an emission judge is not scored for a session, THE SYSTEM SHALL use deterministic `rule-1` emission and record `fallbackReason: 'not-scored'`; WHEN no judge is configured THE SYSTEM SHALL record `fallbackReason: 'no-judge'`.
- **R-17** — WHEN `rule-1` scores a step, THE SYSTEM SHALL award `+2` for a matching intent, `+1` for a matching program, `-0.5` for an identifiable non-match, and `+1` for a tool-name match when no command is present; a file-pattern match SHALL require a command path. It SHALL derive commands, programs, tools, patterns, and optional `skillStep` using the SKIL-128 intent rules and SHALL not introduce new collection or redaction fields.
- **R-18** — WHEN a Skill content hash cannot be resolved by `SkillContentSource`, THE SYSTEM SHALL include the Skill in the eligible state set with `profile: 'missing'` and zero emission evidence; content SHALL be read by exact `contentHash` match only.
- **R-19** — WHEN an alignment reports the largest `skillStep` for a window, THE SYSTEM SHALL derive skipped Skill steps as the missing integers from 1 through that maximum; the emission adapter SHALL not define its own skipped-step semantics.
- **R-20** — WHEN an explicit maintenance operation scores emissions, THE SYSTEM SHALL call the judge outside Projection, write an immutable `emissions` memo keyed by `emission:<judgeVersion>:<inputHash>`, and make Projection read memo rows without invoking the judge.
- **R-21** — WHEN the projection cursor is computed, THE SYSTEM SHALL combine the readable `judges` record and a `derivationKey` hash over sequence-model version, parameter hash, emission version, emission memo count/last id, and the set of resolved Skill-content hashes; any change SHALL force full re-projection, and removing the judge SHALL restore `rule-1` output.

## Derived records and attribution

- **R-22** — WHEN Projection calls `inferSkillAttribution`, THE SYSTEM SHALL use the single pure interface `inferSkillAttribution(observations, { emissions, contents, params })` and SHALL return windows, one `SkillPosterior` per session, and one `FailureAttribution` per failure subject before building Experiences and Failure cases. `EmissionLookup` SHALL resolve a session/input hash to either a validated `EmissionOutput` memo or no result.
- **R-23** — WHEN a `SkillPosterior` is persisted, THE SYSTEM SHALL use id `posterior:<sessionId>`, model `hmm-1`, include parameters and hashes, emission version/source/fallback/input hash, Skills with `ok` or `missing` profiles, `unknownPrefix`, step shares, MAP, window shares, and evidence-time `createdAt`; shares SHALL be rounded to six decimals and sum to 1 within `1e-6`, with ineligible Skills omitted rather than written as tiny probabilities.
- **R-24** — WHEN a `FailureAttribution` is persisted, THE SYSTEM SHALL use id `attribution:<subjectId>`, include origin, session, source, `StateShares`, margin, uncovered flag, contributing step ids, anchor in `tool-call | step | correlation | position | session`, optional anchor Observation, and optional posterior id; `margin` SHALL remain an uncalibrated strength score.
- **R-25** — WHEN a failure subject has explicit `skillName`, THE SYSTEM SHALL assign all share to that Skill and bypass posterior attribution; WHEN it has an `attributionOverride`, THE SYSTEM SHALL preserve the override category and use its explicit Skill target when present; WHEN exactly one Skill was loaded before the subject THE SYSTEM SHALL assign all share to that Skill; WHEN no Skill was loaded THE SYSTEM SHALL assign all share to `none`; otherwise it SHALL use posterior attribution.
- **R-26** — WHEN posterior attribution aggregates a failure subject, THE SYSTEM SHALL use K=3 same-task steps as follows: a `tool-failure` uses its anchor plus the two preceding steps, an implicit follow-up uses the three steps preceding its position, and an anchored explicit feedback uses its anchor plus the two preceding steps; with no prior tool step it SHALL use a forward prediction. It SHALL drop Skill shares below `minShare = 0.1`, normalize retained Skill shares with `none`, and set `uncovered` when `noneShare >= 0.5` unless `unknownPrefix` is true. WHEN either anchor or candidate lacks `taskId`, the task boundary SHALL be the nearest preceding `task-finished` after which only later steps are eligible, or session start when none exists; session fallback ignores task boundaries.
- **R-27** — WHEN an explicit feedback Observation lacks a Skill, THE SYSTEM SHALL locate its anchor in order by `toolCallId`, `stepId`, `correlationIds`, then session-wide average; it SHALL record `anchor` as `tool-call`, `step`, `correlation`, or `session`, while `tool-failure` and implicit follow-up subjects SHALL record `position`, and SHALL not let feedback write time alter SkillWindow boundaries.
- **R-28** — WHEN a failure subject has origin `tool-failure`, THE SYSTEM SHALL create it only for a failed `task-finished` whose final failed ToolAttempt has no same-intent success afterward; exploratory failures in successful tasks SHALL not create this origin, and Correction episodes SHALL remain outside Failure cases.
- **R-29** — WHEN a multi-Skill subject has retained Skill shares, THE SYSTEM SHALL emit one Failure case per Skill with normalized `attributionWeight`, `noneShare`, `uncovered`, `attributionSource`, `attributionId`, and `dominant`; the maximum share SHALL be dominant, ties SHALL use lexicographically smallest Skill, share-one ids SHALL remain `failure:<subjectId>`, and posterior fan-out ids SHALL be `failure:<subjectId>#<skillName>`.
- **R-30** — WHEN Failure clusters are built from weighted cases, THE SYSTEM SHALL preserve `occurrenceCount === cases.length`, add `dominantOccurrence` and `weightedOccurrence`, and leave existing cluster identity and `FailureOrigin` meanings intact while adding `tool-failure`.
- **R-30a** — WHEN `diagnoseFailureCluster` computes evidence strength, THE SYSTEM SHALL use `weightedOccurrence` for occurrence strength and SHALL fall back to `occurrenceCount` for legacy clusters without that field; it SHALL not copy posterior `margin` into `attributionConfidence` or use margin in `confidenceBand`. For equal evidence counts, an all-minority weighted cluster SHALL have no greater diagnosis confidence than an all-dominant cluster.
- **R-31** — WHEN a proposal gate evaluates a Failure cluster, THE SYSTEM SHALL count only dominant cases for both the repeated-evidence and high-severity branches; a minority case SHALL not independently pass the gate, and uncalibrated `margin` SHALL not enter the gate.
- **R-32** — WHEN Experiences are built from a multi-Skill session, THE SYSTEM SHALL group tool steps by MAP Skill, group failures by the largest FailureAttribution share, place MAP `none` in a distinct none group, and SHALL not create an `unattributed` group or infer `not-attributable` merely because multiple Skills exist.

## Downstream metrics, costs, and correction routing

- **R-33** — WHEN `failures` or `metrics` is rendered, THE SYSTEM SHALL expose per-Skill `windows`, `uncertainWindows`, `eligibleSteps`, `dominantSteps`, optional `dominantStepShare`, `expectedSteps`, `attributedFailures`, and `weightedFailures`, plus global `uncoveredFailures` and `noneExpectedSteps`; each Failure line SHALL show weight and attribution source, and the report SHALL include an uncovered section.
- **R-34** — WHEN `metrics()` is called, THE SYSTEM SHALL refresh Projection first and SHALL use the same derived records as `failures()`; existing `followUps` semantics SHALL count the dominant attributed Skill and exclude subjects with no loaded Skill.
- **R-35** — WHEN execution cost is apportioned, THE SYSTEM SHALL use SKIL-130's tool-call and input-plus-output-token definitions, assign expected steps as `sum(p(z_t = k))`, and assign token observations to the adjacent tool step posterior with none as the fallback.
- **R-36** — WHEN a Correction episode is routed, the system SHALL apply rules in this order: existing SKIL-128 rule 0 (already promoted), rule 1 (explicit `--skill`), posterior-aware 2a (majority uncovered => `create-skill`), posterior-aware 2b (one majority dominant Skill => `patch-content` for that Skill), then existing rules 3 and 4. For episodes without posterior data (single Skill, no Skill, or legacy log), 2a/2b SHALL use the original `loadedSkills` rule-2 input. Until SKIL-136 merges, correction-episode references SHALL say “以 SKIL-136 合并版为准”.
- **R-37** — WHEN `calibrateSkillPosteriors` runs, THE SYSTEM SHALL accept a host-provided `CounterfactualReplay` and a host-provided `task`, sample at most the configured number of posterior-attributed sessions deterministically, compare full versus withheld-Skill replays, and write a report without changing Projection, gates, weights, or `derivationKey`.
- **R-38** — WHEN calibration is reported, THE SYSTEM SHALL include replay version, emission version, parameter hash, seed, skipped sessions, posterior-share bins, delta statistics, rank correlation, and Brier/Platt output when sample size permits; a member SHALL explicitly adopt any resulting parameters before they affect posterior records.

## Compatibility and scope

- **R-39** — WHEN existing JSON or Markdown output is extended, THE SYSTEM SHALL preserve existing fields, ids, origin values, cluster ordering, and SKIL-126/SKIL-134 behavior except for the specified multi-Skill and weighted fields; new fields SHALL be additive.
- **R-40** — WHEN the implementation is delivered, THE SYSTEM SHALL include the core interfaces, bundle mapping, window/posterior/attribution stores, rule and judge emission paths, memo operation, downstream reports/metrics, calibration seam, and focused tests; it SHALL exclude runtime behavior changes, Provider rank changes, full counterfactual replay, task-summary collection, new DSH events, and a real judge backend.
