## Design

### Authority and decisions

`docs/design/derived-projection-module.md` is the upstream design background. The accepted boundaries are in ADR-0016 (facts and revisable attribution), ADR-0026 (posterior records, emission memo and full rebuild), and ADR-0034 (memo-backed deterministic Projection). This spec does not amend those decisions or introduce an ADR. The module shape, context-derived key, stored-view proposal input, cursor-resident failure count, and exhaustive intent map are reversible implementation choices from the design: 采用默认答案，成员可推翻。

At spec time `origin/main` has Skill windows and correction records, while SKIL-162's PR #113 is still draft. Tasks 2-5 target the state after #113 merges. Its `skill-posteriors`, `failure-attributions`, and `emissions` registrations and version inputs must be included when that branch lands; they are not optional acceptance items.

### Module boundaries and data flow

`service.ts` delegates to `derivation.ts` (`DerivedProjection`), which owns the cursor lock, key, fast-path read, full rebuild, and cursor-resident counter. `derivation.ts` invokes the synchronous, pure `projectDerived(ctx)` in `projection-steps.ts`; `store-registry.ts` supplies typed store metadata to both persistence and `state-root.ts`. `projection-steps.ts` calls `projectWorkflow` from `workflow.ts`, then computes correction, Skill-window, posterior, and attribution outputs and merges correction Experiences. `workflow.ts` does not import the new module. Existing `store.ts` and `projection.ts` have other purposes and remain untouched.

`STORES` has one entry per store, keyed by camelCase view property and carrying kebab-case disk name, role (`fact`, `memo`, `derived`) and `projectionInput`. `StoreName`, `MemoKey`, `DerivedKey`, `RecordOf<K>`, and `DerivedRecords` derive from it. `resolveLayout` iterates the registry in existing order. `openStores(layout)` creates typed instances and service public fields retain references to those same instances; health and repair still use layout descriptors. Registration plus a projection step is the change needed for a new derived output. A new version source requires one additional version field and source entry.

`DerivationContext` contains Observations, memo arrays keyed by `MemoKey`, content addressed by exact Skill `contentHash`, and `DerivationVersions`. It contains no clock or model callback. `VERSION_SOURCES` maps every version field by constant export name or injected classifier/judge version; `resolveDerivationVersions` is the single reader of those sources. `windowRulesVersion` and `correctionRulesVersion` continue to override key values for testing only. The extracted `projectWorkflow` preserves `EvolutionWorkflow.snapshot()` output. `projectDerived` returns every derived registration plus the correction rejected-drafts counter; `DerivedProjection` augments its view counters with cursor-resident classifier failures.

The derivation key hashes `{ versions, memoFingerprints, skillContentHashes }`. Each memo fingerprint is `{ count, lastId }`, discovered by registry iteration; the content hash list is sorted. The cursor also checks Observation count, last id, and fingerprint. A match reads all derived stores via `DerivedKey`; a mismatch or `force` runs every step. Before replacing any derived store, the module atomically invalidates a matching old cursor while preserving its classifier-failure counter; it writes a valid final cursor only after every replacement succeeds. This covers forced rebuilds with unchanged inputs: even if the final cursor write fails, the old matching cursor cannot validate partially replaced stores. A pre-existing cursor with the former key format misses once, rebuilds, then takes the fast path. No fact or memo store is replaced.

`proposeChange` takes one refreshed `DerivedView.records` and passes its common workflow fields to `proposeFromRecords` outside the lock. This preserves the Designer signature and proposal gate while including correction Experiences. `EvolutionWorkflow.propose()` calls the same function with its own `snapshot()`; its legacy behavior remains. `proposePattern` consumes patterns and episodes from the refreshed view. SKIL-163's later dominant-only proposal gate must be implemented inside `proposeFromRecords` so direct workflow and service calls cannot diverge.

### Intent classification and errors

`follow-up.ts` owns `INTENT_OUTCOME`, `FAILURE_INTENTS`, and `isFailureIntent`, next to `INTENT_POLICY_VERSION`. `Record<FollowUpIntent, IntentOutcome>` covers all nine present intents. A compile-time `FeedbackKind` subset assertion catches a new feedback kind missing from `FOLLOW_UP_INTENTS`; adding the intent then requires an outcome. The three Experience/Failure checks and one metrics check use the helper. This migration preserves the current table and policy version. The root-cause mapping in `experience.ts` serves a different purpose and is outside scope.

Cursor reads/writes and derived replacements run under the existing cursor lock. On a derived or final-cursor write failure, the invalid cursor remains, so a later refresh repeats the full rebuild. `recordClassifierFailure()` increments the count under that lock; refresh and repair carry it forward, while manual cursor deletion still resets it. No model is called by Projection or repair. These rules keep memo preservation and reconstructibility per ADR-0016, ADR-0026, and ADR-0034.

### Test strategy

Core compilation proves missing derived record keys, omitted version-source fields, and unmapped intents fail. `tests/derivation.spec.ts` supplies a nonempty fixture for every derived store and covers G1-G6: forced/fast equivalence; one-at-a-time version invalidation; every memo invalidation; bidirectional `_VERSION` export-name and value checks including same-value different-name negative control; cursor/write/construction whitelist and inline-version guard; and the intent table/version snapshot. The `_VERSION` scan covers projection-step modules present after #113, including emission code. Inline literals remain a residual risk outside the guarded syntax; T3 extracts the known `hmm-1`, `rule-1`, and `skill-windows-v1` literals into named constants.

`tests/correction.spec.ts` owns R1 with ordinary and correction Experiences. `tests/core.spec.ts` owns R2 and layout/old-cursor compatibility. Existing correction, archive health/repair, workflow, and pattern-design tests remain green. T3 includes a temporary old/full-path versus pure-function output comparison while both implementations coexist; T4 removes it after the old path is removed. The implementation acceptance command for each task is `npm --prefix packages/skill-evolution run build` and `npm --prefix packages/skill-evolution test`; touched adapter/bundle packages run their own build/tests when their code is changed.

### Dependencies and scope

T1 can merge before #113 and must precede SKIL-163, which changes `buildFailureCases`. T2-T5 depend on #113/SKIL-162 merging and proceed in order; SKIL-163 and its downstream SKIL-165/166 wait for T5 so stored cluster ids and proposal gates share one path. SKIL-164 overlaps #113's emission memo and key work: its owner/Mika should restrict it to remaining explicit judge/memo operation work and use the module's version input; it must not write a second cursor/key path. SKIL-167 can work in parallel after posterior availability and reads posteriors only; calibration output is not a reconstructible Derived record and does not enter the derivation key. SKIL-173 adds adapter flow, no projection; overlapping `service.ts` edits are merged by the later branch. These sequencing choices are reversible business judgments: 采用默认答案，成员可推翻。

Store disk names, order, paths, record shapes, and cursor field names remain unchanged. `WorkflowSnapshot` and `EvolutionWorkflow` public signatures remain unchanged. `refreshDerived()` narrows its return type to the structural superset `DerivedRecords`; its existing read-only callers remain valid. Validation/repair registration, diagnosis links to correction Experiences, and a new durable fact store for classifier-failure counts are outside scope.
