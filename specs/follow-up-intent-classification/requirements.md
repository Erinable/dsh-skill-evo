## Requirements

### Vocabulary and rule resolution

- **R-1** — WHEN the core resolves a `user-follow-up`, THE SYSTEM SHALL represent its intent as one of `FEEDBACK_KINDS` plus `not-attributable` or `unknown`, preserving an explicit feedback kind as the intent and never emitting `other` from a rule or classifier.
- **R-2** — WHEN a follow-up is resolved, THE SYSTEM SHALL apply the priority `explicit` → valid memo entry for the current classifier version → versioned rule fallback, and SHALL record the selected source and version on the Follow-up resolution.
- **R-3** — WHEN rule fallback is selected, THE SYSTEM SHALL normalize text with NFKC, lowercase, and trim whitespace, then apply the following fixed first-match table. Matching is case-insensitive after normalization; English markers use token/phrase boundaries so `correct` cannot match inside another word. The listed order is normative.

  | Rule id | Markers and matching semantics | Positive examples | Required negative example(s) | Intent / confidence |
  |---|---|---|---|---|
  | `empty` | No text, or normalized text is empty. | missing `text`; `"   "` | `"ok"` | `unknown` / 0 |
  | `correction` | Contains one whole marker or phrase: `不对`, `错了`, `不正确`, `应该是`, `wrong`, `incorrect`, `should be`, `please correct`. | `Please correct step two.`; `Please correct timeout diagnosis.`; `Please correct this.`; `still wrong`; `wrong, upload this again`; `不对，应该…` | `that's correct`; `upload this again` | `incorrect` / 0.6 |
  | `constraint` | Contains one whole marker or phrase: `还要`, `别忘了`, `必须`, `不要`, `make sure`, `must`, `don't`. | `必须保留第二步`; `make sure the path is quoted` | `好的` | `constraint` / 0.5 |
  | `retry` | Contains one whole marker or phrase: `再试`, `重试`, `重新来`, `try again`, `retry`, `redo`. | `retry this command`; `再试一次` | `try this once` | `retry` / 0.6 |
  | `goal-changed` | Contains one whole marker or phrase: `换个话题`, `另一个问题`, `顺便问`, `by the way`, `new task`. | `顺便问一下部署时间`; `by the way, what is the version?` | `upload this again` | `goal-changed` / 0.6 |
  | `acknowledgement` | The entire normalized message consists only of one token from `谢谢`, `好的`, `收到`, `ok`, `thanks`, `great`, plus whitespace or punctuation. | `谢谢！`; `ok.`; `great` | `好的，但是不对`; `好的，接下来改一下标题` | `satisfied` / 0.7 |
  | `continue` | The normalized message starts with a whole marker from `继续`, `接着`, `下一步`, `go on`, `continue`, `next`; the marker must be followed by end of text, whitespace, or punctuation. | `继续`; `继续吧`; `next step` | `new continue` | `not-attributable` / 0.6 |
  | `no-match` | No earlier rule matches. | `upload this again` | `Please correct this.` | `unknown` / 0.2 |
- **R-4** — WHEN a follow-up is `谢谢`, `好的`, `继续`, or one of the acknowledgement/continue markers above, THE SYSTEM SHALL resolve it to a non-failure intent; WHEN it contains a correction marker, THE SYSTEM SHALL resolve it to `incorrect`; because `correction` precedes `acknowledgement`, `好的，但是不对` SHALL resolve to `incorrect`; `好的，接下来改一下标题` SHALL not resolve to `satisfied`; and `that's correct` SHALL not resolve to `incorrect`.
- **R-5** — WHEN an inferred (non-explicit) follow-up has no Skill attribution, THE SYSTEM SHALL attribute it only to the unique Skill loaded earlier in the same session; WHEN there is no such unique Skill, THE SYSTEM SHALL leave the Skill target absent and SHALL not create a Skill Failure case for that follow-up. Explicit feedback follows R-7 even when it has no `skill` field.
- **R-6** — WHEN an inferred follow-up may become a Failure case, THE SYSTEM SHALL resolve preceding tool context by first reading `payload.precedingToolKind` and `payload.precedingToolFailed`; when either field is absent, it SHALL scan backward in the same session from that follow-up to the previous non-explicit `user-follow-up` or session start, using the last `skill-load-requested`, `skill-loaded`, `skill-load-failed`, or `tool-result` Observation in that turn. These corrections SHALL apply only to inferred failures with no valid `attributionOverride`: `skill-load-failed` overrides attribution to `composition` and diagnosis to `edit-metadata`; failed `tool-result` overrides attribution to `tool`, lowers severity to `low`, and diagnoses `not-skill` with `observe-only`. The payload and offline paths SHALL produce the same result.

### Derived failures, diagnosis, and compatibility

- **R-7** — WHEN a resolution is converted to a Failure case, THE SYSTEM SHALL apply this policy table: `incorrect` is explicit `high` / inferred `medium`, attribution `content`, root cause `content` and operation `patch-content`; `constraint` is explicit `low` / inferred `low`, attribution `content`, root cause `boundary` and operation `observe-only`; `retry` is explicit `medium` / inferred `medium`, attribution `unknown`, root cause `content` and operation `patch-content`; `dissatisfied` is explicit `medium` / inferred `medium`, attribution `unknown`, root cause `content` and operation `patch-content`; explicit `other` is `low`, attribution `unknown`, root cause `uncertain` and operation `observe-only`. `satisfied`, `goal-changed`, `not-attributable`, and `unknown` are never Failure cases. Explicit feedback remains an `explicit-feedback` case, including without `skill`; inferred failure intents are `implicit-follow-up` cases with the resolution id, source, and intent.
- **R-8** — WHEN a Failure cluster is diagnosed, THE SYSTEM SHALL use this five-step structured sequence and never free-text substrings: (1) `load-failure` → `composition`; (2) when a case has attribution, `composition`/`content` remain themselves, `tool`/`model`/`task-change`/`not-attributable` → `not-skill`, while `routing`/`unknown` continue; (3) `intent` or `feedbackKind` maps `incorrect`/`dissatisfied`/`retry` → `content`, `constraint` → `boundary`, `goal-changed` → `not-skill`, `other` → `uncertain`; (4) an old `implicit-follow-up` case without `intent` → `content`; (5) otherwise → `uncertain`. Across a cluster it SHALL choose `composition > content > boundary > not-skill > uncertain`; `composition` maps to `edit-metadata`, `content` to `patch-content`, and `boundary`, `not-skill`, or `uncertain` to `observe-only`.
- **R-9** — WHEN `attributionFor` is computed for a group, THE SYSTEM SHALL check in order: any valid override → any `skill-load-failed` → multiple Skills (`not-attributable`) → the first follow-up that becomes a Failure case → `goal-changed` (`task-change`) → `unknown`. Confidence SHALL come from explicit `payload.attributionConfidence` (or 1 when absent), the classifier's returned confidence, or the fixed rule confidence; groups without a follow-up retain the existing evidence-strength calculation.
- **R-10** — WHEN Projection creates a Diagnosis without an explicit `now`, THE SYSTEM SHALL set `createdAt` to the latest `createdAt` among that cluster's evidence cases, so repeated projections over unchanged inputs are byte-for-byte stable.
- **R-11** — WHEN existing JSON or public output is extended, THE SYSTEM SHALL preserve existing fields and ids (`failure:<observationId>`, existing `origin` values, and existing cluster identity rules) while appending follow-up source, intent, attribution, and metrics fields; JSON SHALL only add fields, Markdown failure lines SHALL append `[<severity> · <source>]`, and the migration tests listed in the upstream design §5.1 SHALL remain passing or be updated exactly where the specified behavior changes.

### Classifier and deterministic projection

- **R-12** — WHEN a host injects a Follow-up classifier, THE SYSTEM SHALL accept an object with a `version` and `classify(input, signal)` method through `EvolutionServiceOptions.followUpClassifier`; core SHALL not import DSH modules, and Projection SHALL remain synchronous and never call the classifier.
- **R-13** — WHEN `classifyFollowUps` runs, THE SYSTEM SHALL classify only closed, non-explicit follow-ups, pass at most 20 redacted Observation digests before and after the follow-up plus its unique Skill target, and compute `inputHash` from canonical JSON without timestamps or session sequence numbers; pending inputs SHALL use rules until closed.
- **R-14** — WHEN classifier output is valid, THE SYSTEM SHALL append an immutable Classification memo entry keyed by `classification:<classifierVersion>:<inputHash>`; WHEN an individual call times out, throws, or returns an invalid intent/confidence, THE SYSTEM SHALL record a per-item failure, write no memo for that item, continue independent items, and fall back to rules. WHEN the caller signal is aborted, THE SYSTEM SHALL stop starting new items while preserving memo rows already written.
- **R-15** — WHEN the classifier is absent, `classifyFollowUps` SHALL fail with the documented `classifier-unavailable` operation error; WHEN its version or input changes, the Projection cursor SHALL invalidate and rebuild all Derived records without invoking the classifier.
- **R-16** — WHEN the service repairs the root, THE SYSTEM SHALL health-check and isolate malformed memo rows without deleting or rewriting valid Classification memo bytes; repair and forced Projection SHALL not call the classifier, and only derived stores (including `follow-ups.jsonl`) may be replaced.
- **R-17** — WHEN metrics are aggregated, THE SYSTEM SHALL add `followUpIntents` totals, failures, and per-intent counts split by `explicit`, `classifier`, and `rule`, while preserving the existing `followUps` and `followUpRate` semantics.

### Runtime boundary and scope

- **R-18** — WHEN the default bundle mapper writes a `user-follow-up`, THE SYSTEM SHALL add optional core-valued `precedingToolKind` and `precedingToolFailed` fields computed from the current session turn, clear the turn state at each human user message, and keep the mapping synchronous without classifier calls.
- **R-19** — WHEN the implementation is delivered, THE SYSTEM SHALL include the core interface, rule resolver, memo, explicit classification operation, projection/cursor changes, bundle fields, and fake-classifier acceptance tests; it SHALL exclude a real classifier backend, `/skill-evolution classify`, and any CLI entry point for classification.
