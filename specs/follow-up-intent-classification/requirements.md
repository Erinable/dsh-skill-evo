## Requirements

### Vocabulary and rule resolution

- **R-1** — WHEN the core resolves a `user-follow-up`, THE SYSTEM SHALL represent its intent as one of `FEEDBACK_KINDS` plus `not-attributable` or `unknown`, preserving an explicit feedback kind as the intent and never emitting `other` from a rule or classifier.
- **R-2** — WHEN a follow-up is resolved, THE SYSTEM SHALL apply the priority `explicit` → valid memo entry for the current classifier version → versioned rule fallback, and SHALL record the selected source and version on the Follow-up resolution.
- **R-3** — WHEN rule fallback is selected, THE SYSTEM SHALL normalize text with NFKC, lowercase, and trim whitespace, then apply the fixed first-match table: empty→`unknown` (0), correction→`incorrect` (0.6), constraint→`constraint` (0.5), retry→`retry` (0.6), goal-change→`goal-changed` (0.6), acknowledgement→`satisfied` (0.7), continue→`not-attributable` (0.6), and no-match→`unknown` (0.2).
- **R-4** — WHEN a follow-up text is `谢谢`, `好的`, `继续`, or their listed English equivalents, THE SYSTEM SHALL resolve it to a non-failure intent; WHEN it contains a correction marker such as `Please correct step two.`, `Please correct timeout diagnosis.`, `Please correct this.`, or `不对，应该…`, THE SYSTEM SHALL resolve it to `incorrect`; WHEN it is `that's correct`, THE SYSTEM SHALL not resolve it as `incorrect`.
- **R-5** — WHEN an inferred (non-explicit) follow-up has no Skill attribution, THE SYSTEM SHALL attribute it only to the unique Skill loaded earlier in the same session; WHEN there is no such unique Skill, THE SYSTEM SHALL leave the Skill target absent and SHALL not create a Skill Failure case for that follow-up. Explicit feedback follows R-7 even when it has no `skill` field.
- **R-6** — WHEN an inferred failure follows `skill-load-failed`, THE SYSTEM SHALL override attribution to `composition` and diagnosis to `edit-metadata`; WHEN it follows a failed `tool-result`, THE SYSTEM SHALL override attribution to `tool`, lower severity to `low`, and diagnose `not-skill` with `observe-only`; an explicit `attributionOverride` SHALL take precedence over both corrections.

### Derived failures, diagnosis, and compatibility

- **R-7** — WHEN a resolution intent is `satisfied`, `goal-changed`, `not-attributable`, or `unknown`, THE SYSTEM SHALL persist the Follow-up resolution but SHALL not create a Failure case; WHEN the intent is an inferred `incorrect`, `constraint`, `retry`, or `dissatisfied`, THE SYSTEM SHALL create an `implicit-follow-up` Failure case with the resolution id, source, intent, and applicable severity; explicit feedback SHALL remain an `explicit-feedback` case regardless of whether `skill` is present.
- **R-8** — WHEN a Failure cluster is diagnosed, THE SYSTEM SHALL use structured origin, attribution, and `intent`/`feedbackKind` only, with precedence `composition > content > boundary > not-skill > uncertain`, and SHALL map `incorrect`/`dissatisfied`/`retry` to `content`, `constraint` to `boundary`, `goal-changed` to `not-skill`, and load failures to `composition`; it SHALL not infer root cause from free-text substrings.
- **R-9** — WHEN Projection creates a Diagnosis without an explicit `now`, THE SYSTEM SHALL set `createdAt` to the latest `createdAt` among that cluster's evidence cases, so repeated projections over unchanged inputs are byte-for-byte stable.
- **R-10** — WHEN existing JSON or public output is extended, THE SYSTEM SHALL preserve existing fields and ids (`failure:<observationId>`, existing `origin` values, and existing cluster identity rules) while appending follow-up source, intent, attribution, and metrics fields; the migration tests listed in the upstream design §5.1 SHALL remain passing or be updated exactly where the specified behavior changes.

### Classifier and deterministic projection

- **R-11** — WHEN a host injects a Follow-up classifier, THE SYSTEM SHALL accept an object with a `version` and `classify(input, signal)` method through `EvolutionServiceOptions.followUpClassifier`; core SHALL not import DSH modules, and Projection SHALL remain synchronous and never call the classifier.
- **R-12** — WHEN `classifyFollowUps` runs, THE SYSTEM SHALL classify only closed, non-explicit follow-ups, pass at most 20 redacted Observation digests before and after the follow-up plus its unique Skill target, and compute `inputHash` from canonical JSON without timestamps or session sequence numbers; pending inputs SHALL use rules until closed.
- **R-13** — WHEN classifier output is valid, THE SYSTEM SHALL append an immutable Classification memo entry keyed by `classification:<classifierVersion>:<inputHash>`; WHEN an individual call times out, throws, or returns an invalid intent/confidence, THE SYSTEM SHALL record a per-item failure, write no memo for that item, continue independent items, and fall back to rules. WHEN the caller signal is aborted, THE SYSTEM SHALL stop starting new items while preserving memo rows already written.
- **R-14** — WHEN the classifier is absent, `classifyFollowUps` SHALL fail with the documented `classifier-unavailable` operation error; WHEN its version or input changes, the Projection cursor SHALL invalidate and rebuild all Derived records without invoking the classifier.
- **R-15** — WHEN the service repairs the root, THE SYSTEM SHALL health-check and isolate malformed memo rows without deleting or rewriting valid Classification memo bytes; repair and forced Projection SHALL not call the classifier, and only derived stores (including `follow-ups.jsonl`) may be replaced.
- **R-16** — WHEN metrics are aggregated, THE SYSTEM SHALL add `followUpIntents` totals, failures, and per-intent counts split by `explicit`, `classifier`, and `rule`, while preserving the existing `followUps` and `followUpRate` semantics.

### Runtime boundary and scope

- **R-17** — WHEN the default bundle mapper writes a `user-follow-up`, THE SYSTEM SHALL add optional core-valued `precedingToolKind` and `precedingToolFailed` fields computed from the current session turn, clear the turn state at each human user message, and keep the mapping synchronous without classifier calls.
- **R-18** — WHEN the implementation is delivered, THE SYSTEM SHALL include the core interface, rule resolver, memo, explicit classification operation, projection/cursor changes, bundle fields, and fake-classifier acceptance tests; it SHALL exclude a real classifier backend, `/skill-evolution classify`, and any CLI entry point for classification.
